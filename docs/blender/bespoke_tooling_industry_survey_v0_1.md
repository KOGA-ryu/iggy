# Bespoke Blender tooling — industry survey v0.1 (for the factory lanes)

2026-07-29 · Method: four parallel research passes (studio pipelines & headless automation; procedural-generation ecosystems; addon/extension engineering practice; GN frontier + agent-driven Blender + rigging), primary sources where reachable. Entry in the Blender-workflow research series after [ai_blender_workflow_extract_v0_1.md](ai_blender_workflow_extract_v0_1.md); Blender-side companion to `docs/creative_engine_tools_industry_survey.md` and, like it, intended as a **cut-source for batches** (§9). Sourcing caveat up front: `blender.org` / `studio.blender.org` / `projects.blender.org` / `download.blender.org` all 403'd our fetchers, so some claims about those properties come from search snippets of the official pages plus secondary sources; everything shaky is aggregated in §10.

Factory context this survey is judged against: headless Python→bpy generation targeting **Blender 5.1.1 (build `b70da489d7f4`)**, deterministic all-quad donors, `SINC_` GN node-group library with the Python/idempotency contract, linter + pytest gates + plate renders, LLM agents driving, Ace never in the Blender UI.

## 0. Headline findings

1. **We are sitting on a version cliff.** Blender **5.2 LTS shipped 2026-07-14** (two weeks ago; supported to ~Jul 2028). Our 5.1.x target is a non-LTS release that just fell out of the current window — and **PyPI deletes `bpy` wheels outside the current LTS window** (archive moves to `download.blender.org/pypi/`). 5.2 also rewrites the GN-modifier-input Python API and changes Compare/Random Value **socket identifiers** — both squarely inside our node-authoring contract. Decision needed: mirror-and-hold on 5.1.1, or plan the 5.2 hop with a golden-plate re-baseline. §1.
2. **Our doctrine has a proof-at-scale peer, and it's BSD-licensed.** Princeton's **Infinigen** (and its 2026 spin-out **ProcFunc**) is our exact architecture — Python as source of truth, transpiled GN, seed discipline, headless gates — run at hundreds-of-generators scale, **BSD-3-Clause** (vendorable, outputs unencumbered). ProcFunc's stated purpose is making procedural Blender code editable by LLMs — our operating model, validated by a serious lab. §2.
3. **The anatomy program's blueprint already exists in production code.** Rigify's staged mode-batched generation (names-as-handles, ORG/MCH/DEF layering), CloudRig's generation-log (our validate→REPAIR→receipt doctrine, shipped), MPFB2's **JSON rigs with landmark-anchored bone placement**, and Epic's weight-inpainting transfer algorithm together form a near-complete pattern set for the 220-bone joint-graph program. §7.
4. **Blender's own regression harness is the upgrade path for our plate gates**: `oiiotool --fail 0.016 --failpercent 1` against committed references, HTML triage reports, `BLENDER_TEST_UPDATE=1` reference regeneration, expected-object mesh comparison for GN, and a **blocklist for non-deterministic tests instead of mushy thresholds**. Concrete numbers and files to copy. §4.
5. **Blender.org runs an official lab MCP server** with two ideas worth importing even though we skip MCP itself: background-process `execute_blender_code_for_cli` variants, and **`get_python_api_docs`** — bundled exact-version bpy RST served to the agent. Meanwhile the popular community BlenderMCP has a CVE and an SSRF and is the wrong shape for us. Published agent-driven-Blender SOTA is *behind* our test-gated setup. §6.

Strategic backdrop: the Blender Foundation's public AI posture (Apr–May 2026, incl. the capped Anthropic donation) is "assistive yes, generative no" — which lands exactly on our lane doctrine. License landscape: research stack = BSD (safe to vendor); addon world = GPL (fine for internal use, outputs ours); commercial GN products increasingly ship **proprietary node-group "engines"**, one of which (Geo-Scatter) contractually bans third-party scripts touching its nodes — hostile to agent automation; pattern-donor only. §8.

## 1. Version ground truth, mid-2026

| Release | Date | Notes |
|---|---|---|
| 4.5 LTS | Jul 2025 | Last LTS of the 4.x line; still maintained (4.5.9 ~Apr 2026). Reportedly the last with an Intel-mac build (§10) |
| 5.0 | 2025-11-11 | Bundles/closures; big Python API breaks; **Random Value node output changed** (any pre-5.0 seeds regenerate differently) |
| 5.1 | ~2026-03-17 | **Our target.** Python 3.11→**3.13** (VFX Platform 2026); Bone Info node; node tools become per-asset operators (old node tools must be re-saved) |
| **5.2 LTS** | **2026-07-14** | Current LTS, supported ~2 yrs. Lists, geometry bundles, **Mesh Bevel node**, node-tool inputs assignable from Python, `gpu.init()` for `--background` GPU |

Operational facts:

- **One Blender ↔ one Python.** 5.0 = cp311; 5.1/5.2 = cp313. Pin the pair.
- **`bpy` wheel retention:** current release 5.2.0 (2026-07-14, PyPI). Wheels **outside the current LTS window get removed from PyPI**; archive lives at `download.blender.org/pypi/bpy/`. If any part of the box pipeline pip-installs bpy 5.1.x, expect that install path to 404 eventually. **Mirror the exact 5.1.1 artifacts (app build + wheel if used) into our own store now, regardless of the hop decision.**
- The bpy module imports **once per process** (no reload) and has no framebuffer headless — subprocess-per-job, which is already our discipline. Cycles CPU renders fine headless; EEVEE/GPU needs a context (5.2's `gpu.init()` improves the story in `--background`).

**5.1 → 5.2 migration traps** (the live ones for us; 5.0's traps are already behind our target):

| Trap | What breaks |
|---|---|
| GN modifier input API rewritten | `modifier["Socket_2"] = x` / `identifier_use_attribute` → `modifier.properties.inputs.<identifier>.value` / `.type = "ATTRIBUTE"` / `.attribute_name`. Every headless script that sets modifier inputs by identifier migrates |
| Compare + Random Value **socket identifiers changed** | Node-*authoring* code that addresses those sockets by identifier (our contract resolves by identifier, never index — this is the one place that convention bites) |
| Determinism re-baseline | Any node behavior change ⇒ golden plates and expected meshes need a regeneration pass, done deliberately in one batch |

Pull factors for the hop: LTS runway to ~2028, Mesh Bevel node, lists + geometry bundles (§5), Python-assignable node-tool inputs (makes headless node-tool invocation practical), remote asset libraries. Recommendation: **treat the hop as a planned single batch** (migrate the two API surfaces, re-baseline plates/meshes, re-run full suite) rather than drifting; but the mirror-now step is unconditional and cheap.

Also live now, on 5.1: `material.use_nodes` / `world.use_nodes` are deprecated no-ops with removal pre-announced for 6.0 — worth a lint rule today so dead idiom stops accreting.

## 2. Proof-at-scale peers: Infinigen, ProcFunc, BlenderProc

### Infinigen (Princeton Vision & Learning Lab) — deep dive

Research-grade procedural world/asset generator: hundreds of Python+GN generators (nature, indoors, articulated objects) run headlessly. **BSD-3-Clause** — vendorable, generated assets unencumbered, commercially usable. Active: v1.19 "Articulated" (2025-11, 18 articulated categories with joint metadata), **v2.0.0a1 (2026-07-15)** — a rewrite on ProcFunc with one-line `uv run infinigen` CLI. Papers CVPR'23/'24, '25, ProcFunc arXiv:2604.26943. https://github.com/princeton-vl/infinigen

Architecture worth stealing (verbatim patterns, not inspiration):

- **Two-level seeding.** `AssetFactory.__init__(factory_seed)` draws *all* randomizable parameters inside `with FixedSeed(factory_seed):` — factory seed = asset identity; a separate per-instance seed drives `spawn_asset(seed)` variation. Determinism = seeds wrap every stochastic call at *draw* time, never at build time. Audit our generators against this split.
- **Node transpiler.** Canonical loop: author GN in the UI (optional) → transpile to Python → **commit the Python as source of truth**. Emits `shader_material(nw)` / `geometry_nodes(nw)` functions over **NodeWrangler**, their thin node-authoring API (nodes-as-code, not raw `nodes.new()`).
- **Registration seam.** `surface.add_material(obj, fn, selection=…)` / `surface.add_geomod(obj, fn, selection=…, attributes=[…])` — one uniform way to attach shader/GN logic with selection masks. Cleaner than ad-hoc attachment; compare to our mask-attribute contract.
- **Constraint-based layout (Indoors):** Python expression-graph DSL → memoized evaluator over **trimesh proxies** (not bpy meshes) → **simulated annealing** with a typed move set, greedily partitioned per stage. Semantics (asset→room-role mapping) in one file, separate from the solver. Directly relevant to any future room/interior dressing pass — and the proxy-geometry evaluation trick is relevant to *any* expensive spatial validation we run.
- **Ops discipline:** gin-config parameterization, coarse/populate/render task split, `manage_jobs` batch orchestration, seed-stamped output dirs, **paper-pinned stable branches** as reproducibility anchors (their version of our gate tags). Shader displacement **baked to real mesh displacement before export** so exports are self-contained.

### ProcFunc — the 2026 spin-out (watch item, highest strategic relevance)

Infinigen's core extracted to a pip library: **Primitives API + GN→Python transpiler + tracer**, explicitly designed so **LLMs can write and edit procedural material/geometry code with fewer errors** — a serious lab publishing our operating model as a paper. Pre-1.0, pushed 2026-07-18, BSD-3. **Pinned to Blender 4.2.0 + Python 3.11 — behind us**, so pattern quarry + watch item, not a dependency. https://github.com/princeton-vl/procfunc

### BlenderProc (DLR)

Synthetic-data pipeline; GPL-3 (irrelevant for internal use); pinned to Blender 4.2.1, cadence slowing. Two stealable patterns: the **pip-package-that-owns-its-Blender-install** bootstrap (`blenderproc run script.py` re-executes your script inside its managed Blender), and its **writer discipline** (HDF5/COCO/BOP annotation writers as first-class pipeline stages). As a dependency: no. https://github.com/DLR-RM/BlenderProc

Version control findings worth recording: Blender Studio still runs **SVN for .blend files** (uncompressed blends delta well) but their own benchmark post concludes Git/Mercurial(+LFS) are the only viable successors; there is **no semantic .blend diff anywhere** — the industry's real answer is ours (text sources, blends as build products). **Asset catalogs are a plain-text sidecar** (`blender_assets.cats.txt`, UUID:path:name lines) and assets are markable from Python (`id.asset_mark()`, `asset_data.catalog_id`, generated previews) — so the factory can emit a fully catalogued asset-browser library headlessly for Ace's browsing without any UI step.

Corporate half-life lesson (pattern 9 of the studio pass): Ubisoft Mixer dead (2021), Embark blender-tools archived (2026-06), Epic's BlenderTools alive only as a community fork; survivors are Foundation/Studio projects, community forks, and research labs. **Weight long-term bets toward Foundation-owned or BSD research code; treat commercial addons as replaceable.**

## 4. Engineering practice: testing, typing, CI, packaging, churn

### How Blender regression-tests itself (copy these numbers)

From `tests/python/modules/render_report.py` + the developer handbook:

- **Render tests:** each committed .blend renders frame 1 → PNG, compared to a committed reference via **OpenImageIO `oiiotool --fail 0.016 --failpercent 1`** (defaults). Failures emit an **HTML triage report** (new/reference/diff side by side). References regenerate with **`BLENDER_TEST_UPDATE=1`**. Threshold policy: one strict reference platform; elsewhere bump `failpercent` first, then threshold; **non-deterministic tests go on an explicit blocklist rather than getting mushy thresholds**.
- **GN tests:** the .blend contains `test_object` + `expected_object`; runner applies all modifiers and **compares the resulting mesh**; the update flag auto-creates the expected object. Essentials assets are *linked, not packed*, so upstream changes are actually exercised.
- **I/O tests:** md5 checksums of exported files. **Batching:** many tests per Blender launch to amortize startup, with an un-batch flag for hunting cross-test interference.

Verdict: our plate/visgate discipline predates seeing this; upgrading it to the oiiotool-with-thresholds + HTML-triage + update-flag + blocklist shape is a small batch with outsized review-loop payoff (§9 B2).

### The rest of the playbook (deltas against what we already do)

- **Typing:** `fake-bpy-module` (nutti) is the answer, full stop — actively generated (a `-latest` release shipped the day of this survey), MIT, per-version packages; there are no official stubs and none coming. Run pyright/mypy against factory code with zero Blender present.
- **Interactive debugging** (rare for us): `blender_vscode` (Jacques Lucke; alive, pushed 2026-07) + debugpy attach. Cold-start-per-run stays our discipline; hot reload is a UI-addon convenience.
- **CI:** `BradyAJohnston/setup-blender` GH Action (installs + caches Blender per version) or `blender-downloader` + cache. Hosted runners are CPU-only — Cycles CPU works, EEVEE/GPU parity needs self-hosted GPU. The once-canonical nytimes docker images are dormant (ceiling: Blender 3.3); the mid-2026 community pattern is python:3.13 base + pip bpy for logic, plain Blender tarball for `-b` integration jobs. `pytest-blender` exists (v3.0.8, 2026-04) if we ever need suites *inside* the artist build; 5.x compatibility unverified.
- **Packaging (edge only):** the Extensions platform (`blender_manifest.toml`, bundled wheels, declarative `[permissions]`) is mature, and **private distribution is first-class**: `blender --command extension server-generate --repo-dir=…` emits a static `index.json` — a free in-house update channel if we ever ship Ace a review-helper addon. The headless core needs none of it.
- **API-churn firewall** (the recurring killer across every pass): (a) one compat module with `bpy.app.version` guards, never inline scatter; (b) maintain our **own** breakage log of the API surface we touch (MCprep's `BlenderChanges.md` is the model — and note even that lags); (c) read `release_notes/X.Y/python_api/` at every bump — 5.0 pre-announces 6.0 removals, so we can lint today; (d) treat **stdout/log format as unstable** (5.0 changed background-render progress output under farms' feet — relevant to our capture loop).
- **Headless hygiene** (confirms our contract): lookup-or-create naming, explicit remove of prior outputs, `orphans_purge` before save, never trust `.001` suffixes; `foreach_set/get` + flat numpy for bulk mesh data (community benchmark ~25M verts/s-scale vs 60×-slower naive loops; secondary source), `from_pydata` fine below ~50k verts; note 5.0's mathutils **float32 buffer** semantics in numpy interop.
- **Addon exemplars** (what "bespoke tooling done well" looks like): **Rigify** (in-tree; §7 — the generator-architecture model); **Molecular Nodes** (the best public reference implementation of the modern stack: extension packaging + bundled scientific wheels + pytest + CI matrix + docs site + **Python wrapper API over a shipped GN node-group library** — the same shape as our factory's libraries; steal its CI/packaging wholesale); **HumGen3D** (open GPL code / paid assets split, headline feature is a documented `Human` facade API so pipelines never touch the UI — our "automation never enters the UI" doctrine as a product); **Animation Nodes** (cautionary: a bespoke node *runtime* beside core got obsoleted by core — build ON GN, not parallel to it; its author now leads GN development).

## 5. GN frontier for tool authors (what changed 4.5 → 5.2)

On our current target (≤5.1) we already have: import nodes (PLY/OBJ/CSV/STL/Text/VDB directly in GN, 4.5), Set Mesh Normal (4.5), the **GeometrySet Python API** for reading evaluated geometry (4.5 — relevant to headless linting of GN outputs), **bundles** (struct-like packaging of any GN type) and **closures** (caller-supplied node logic — function pointers for node trees) from 5.0, volume grids (5.0), **bundle key-paths with computed string keys** (5.1 — bundles become addressable dicts), **Bone Info node** (5.1 — GN reads per-bone pose/rest transforms; first real rig↔GN bridge), and node tools registered as **individually addressable operators** with custom `bl_idname` (5.1).

Closure mechanics that matter for the `SINC_` contract: **interfaces are name-matched, not positional**; sync-sockets auto-updates signatures on first link only; a muted/unconnected Evaluate Closure passes through same-named inputs→outputs (clean optional-hook pattern); debugging inside multi-context closures is explicitly bad (inspection picks one context "basically at random"). Treat bundle/closure signatures as **schemas and version them like sockets**.

5.2 adds (pull factors for the hop): **geometry-attached bundles** (arbitrary data — even fields/closures — riding along with geometry across modifier/object boundaries), **lists** as a core type, **Mesh Bevel node**, Transfer/Rename/Get-Attribute-Names, node-tool inputs assignable from Python, recursive closures, experimental XPBD physics on the bundle architecture.

Direction (Sept-2025 GN workshop): modal node tools with per-tool keymaps, solver nodes (Bullet/Jolt exposure experiments), default-inputs-computed-by-node-groups, multi-object node tools. GN is becoming a data-structure language; nothing announced obsoletes Python-side generation — and **GN still cannot create armatures** (§7).

Library-engineering state of the art: node groups as **asset-cataloged datablocks**; Blender 5.0's **Essentials "packing"** (linked node-group assets also stored in-file, keeping files self-contained) is now the reference mechanism for shipping node-group libraries; 5.2 adds remote asset libraries. No community versioning convention for node-group assets exists beyond name-suffixing — our idempotency contract is ahead of the field.

Ecosystem quick verdicts: **NodeToPython** v4.2.0 (2026-07-11, supports 4.2–5.2, GPL, on extensions.blender.org) converts any existing node group into clean rebuild-Python — **adopt as a harvest verb** for pulling community/marketplace setups into our idiom (GPL is dev-time only; output is a transcription of the tree). **pynodes** / **geonodes** / **geometry-script** are the Python→GN DSL neighbors — API-ergonomics reading, not dependencies (geometry-script semi-dormant; geonodes active but **no license file**; all Blender-5.x-unverified). **Higgsas / Erindale** toolkits: commercial node-group mega-libraries, pattern-donors for library organization. **Sverchok** is an alternative runtime, not a GN authoring aid — low fit. Marketplace **building generators** converge on one grammar: curve/footprint → floor extrusion → facade **module instancing from named collections** — the kit is swappable, the grammar is stable; exactly compatible with our kit doctrine (Buildify is the free reference implementation, apparently unmaintained since ~3.2-era).

## 6. Agent-driven Blender: the field vs us

- **BlenderMCP** (ahujasid; ~25k stars, MIT, pushed daily): the de-facto community bridge — TCP socket addon inside Blender + MCP relay; arbitrary `execute_blender_code`, viewport screenshots, PolyHaven/Sketchfab/Rodin/Hunyuan asset imports; anonymous telemetry. **Security posture is weak by design**: unauthenticated arbitrary RCE by construction (CVE-2026-10688 filed), SSRF via asset-import URL (issue #203). Its value-adds target interactive GUI sessions, and its gen-AI mesh imports conflict with our provenance gate. **Skip**; if ever run for demos, localhost-only.
- **Official Blender lab MCP server** (`projects.blender.org/lab/blender_mcp`) — the sleeper finding. Deliberately small; same extension+relay shape but with the right headless instincts: **`execute_blender_code_for_cli` variants that open a .blend in a background Blender process** (synchronous completion required — same contract our capture loop assumes), blend-file summaries (datablocks, missing files, linked-library tree), and **`get_python_api_docs`** — bundled exact-version bpy RST + manual excerpts served to the LLM. Lab-stage, no releases. **Steal two ideas**: the background-CLI tool shape, and shipping versioned API docs into agent context instead of letting agents guess bpy signatures (§9 B7).
- **Research systems** (SceneCraft, LL3M, ShapeCraft, CityX — 2024–2026): all converge on "**LLM writes bpy Python**, with code execution as the real API"; nobody has robust direct node-graph manipulation (RNA-level link/zone editing too verbose/error-prone), node-tree serialization for LLMs is unsolved (community JSON hacks), and **screenshot feedback loops are the weakest link** — coarse, token-hungry, blind to topology/scale errors a mesh linter catches. Assessment: our deterministic-generators + machine-checkable-gates position is **ahead of published SOTA**, not behind. The one published thing we lack and should note: LL3M-style retrieve-docs-then-write loops — same fix as the lab MCP's docs tool.
- **Foundation AI posture** (verified 2026): after the Apr-2026 Anthropic Dev-Fund patronage → community backlash → May-2026 cap to a one-off donation, the chairman stated **"no generative AI functionality is currently available or planned"** in Blender; formal AI policies pending; lab experiments framed assistive-not-generative. Two takeaways: (a) our split — agents drive *tooling*, humans own *art*, generation quarantined to the diffusion lane with provenance tags — is exactly the community-legible safe harbor; (b) community sensitivity is real; if any of our tooling ever goes public, lead with the assistive framing and provenance discipline.

## 7. Rigging & the anatomy program: the blueprint is assembled

The joint-graph → 220-bone program can be composed from four production-proven patterns:

1. **Rigify's stage machine** (bundled addon; the canonical code pattern). Component model: each rig type = a Python `Rig(BaseRig)` module keyed off a string on a metarig bone; third-party "feature sets" extend the registry. **Staged generation runs every stage for all rigs before the next, each stage in a fixed mode**: `initialize` (Object) → `prepare_bones` (Edit) → `generate_bones` (Edit — the *only* stage that may add bones) → `parent_bones` (Edit) → `configure_bones` (Object) → `preapply_bones` → `apply_bones` (Edit: bake temp constraints into rest pose) → `rig_bones` (Object: constraints+drivers) → `generate_widgets` → `finalize`. The load-bearing gotcha, stated in their docs: **mode switches invalidate `EditBone`/`PoseBone` references — only bone *names* may be stored between stages** (the `bones` dict of org/ctrl/mch/deform name lists). Bone-prefix layering: **ORG-** (copied spec), **MCH-** (mechanism), **DEF-** (deform — the only bones game export cares about). Adopt the stage machine, names-as-handles, and prefix contract wholesale.
2. **CloudRig** (Blender Studio): same metarig→generate→regenerate loop with per-bone component assignment, component **inheritance**, and two pieces to steal: the **Generation Log** — post-generate detection (never auto-fix) of mistakes with suggested one-click repairs, i.e. our validate→REPAIR→receipt doctrine already shipped in a production rigger — and the **escape-hatch ladder**: declarative Single-Control component → named Bone-Tweak override → arbitrary post-generation script. That ladder is the right API shape for Ace's redlines against generated rigs.
3. **MPFB2** (MakeHuman successor; active, v2.0.16 2026-06, extensions.blender.org): rigs defined **entirely as JSON** (`rig.default.json` + parallel `weights.*.json`); per-bone head/tail each carry a **placement `strategy`** — `"CUBE"` (named joint landmark on the basemesh, e.g. `joint-spine-1`), `"VERTEX"` (index), with `default_position` fallback — plus roll/parent/connect flags. **Landmark-anchored placement instead of absolute coordinates is the right substrate for our joint-graph spec**: bones survive proportion edits, and the founding 220-bone spec's shape-type primitives map naturally onto named landmark geometry.
4. **Robust Weight Transfer** (free addon implementing Abdrashitov et al., Epic, SIGGRAPH Asia 2023): distance+normal-gated direct transfer, then **weight inpainting** fills uncovered regions — the algorithm to put behind the factory's skinning step (body→clothing/armor without manual cleanup); reference code exists in both addon and paper-repo form, straightforward to headless-ify.

Supporting facts: **Auto-Rig Pro** (commercial, ~3.78.x, reportedly 5.1-compatible) matters as retarget/export reference only; **HumGen3D**'s public `Human` API is the character-generation-as-API precedent. **Bone Info** (5.1) opens rig-driven GN (muscle bulge, armor fitting read bone transforms) but the reverse is closed — **GN cannot create or output armatures; programmatic skeleton construction stays a bpy job**, so the program's architecture is future-proof against announced GN work.

bpy armature gotchas for the program (5.x-current): `edit_bones` exists only in Edit mode; constraints/drivers only on `pose.bones` outside it — batch by mode (that's *why* Rigify's stage machine exists). 5.0 changed bone selection/visibility APIs (`Bone.select*` removed → `edit_bones[i].select*` + separate `pose.bones[i].hide`) — 4.x-idiom scripts silently change behavior. Bone collections replaced numbered layers (4.0). Any programmatic animation must use the **slotted Action API** (channelbags; `anim_utils.action_ensure_channelbag_for_slot`) — legacy `action.fcurves` is gone in 5.0. If the rig program stamps per-bone metadata, note 5.0's IDProperty storage split duplicated bone custom-props from old files.

## 8. Procedural ecosystems, product shapes, and the license map

- **The kit-instancing grammar is industry-converged** (§5): footprint/curve → extrude → instance modules from named collections, attribute-driven variation. Our building kits already match; the survey found nothing structurally better — validation, not homework.
- **Product architecture** for asset ecosystems, twice-confirmed (polygoniq engon `.paq`; Geo-Scatter `.scatpack`): **small open-source code addon + versioned binary asset packs resolved by name through a registered asset library; assets linked, not appended**. This is the shape if the factory's kits ever productize, and the name-resolution-through-catalog pattern is a tidy upgrade path for our kit rosters today.
- **License map:** research stack (Infinigen/ProcFunc) = **BSD-3** — vendor freely, outputs unencumbered. Addon world = **GPL** by Blender-API necessity — fine for internal tooling, outputs always ours; only matters if we distribute code. Commercial GN products increasingly split GPL scripts from **proprietary node-group engines** — and **Geo-Scatter's terms explicitly prohibit scripts "from unknown sources" interacting with their nodes**, i.e. contractually hostile to LLM-driven automation. Rule: **no proprietary node-group engine enters the factory's dependency graph**; commercial tools are pattern-donors only. (Geo-Scatter is otherwise the only major commercial tool verified current on 5.1/5.2 — v5.6.3/5.6.4, Jul 2026.)
- Graveyard (don't build on): GScatter (vendor pivoted out of 3D), Buildify (~3.2-era), Mixer, Embark tools, original Epic BlenderTools, Animation Nodes (superseded by GN), nytimes docker images.
- Adjacent research worth one line each: **CityX** (LLM multi-agent plan→validate→execute emitting Blender programs — closest published analogue to our box crew); **Infinigen-Stereo** (pipeline tuned as a data distribution); **ProcTex** (text-to-texture for part-based procedural models — relevant someday to re-skinning parameterized kits).
